# FWM 과학 문서의 역할·보존·발행 원칙

사용자 지시 확정: 2026-09-18. **Grand Challenge의 중간 단계와 완료 이후 모두 적용.** 과제의 완료 상태나 버전 번호 변경으로 폐기하지 않음.

**세 문서의 역할**

| 문서 | 주된 질문 | 소유 내용 |
|---|---|---|
| Squeezing report | 시뮬레이션은 실험과 얼마나 맞는가? 어디까지 탐색했고 어떤 조건이 유망한가? | 관측량·측정면·입력 정의, 문헌/실험 대조, fitting과 holdout 구분, gain·S₋·RF bandwidth, parameter/frontier 탐색, tolerance·불확도·검증 도메인 |
| Analytic reconstruction | 어떤 가정에서 어떤 식이 성립하며 얼마나 정확한가? | 규약·원자/저장고 모델, 정규화, 유도·증명·반례, 평균장과 요동, 전파·검출, 근사 오차·수렴·독립 참조, 이론의 적용 범위 |
| Quotient structure | 어떤 입력·가정·명제가 어떤 결론을 허용하는가? | 이론의 논리적 의존관계, 객체/사상/동치/부분순서의 정의, 정확한 축약과 정보 손실, 분기·합류·병렬 관계, 결론별 필요조건·검증 근거 |

세 문서는 같은 물리·기호·수치 근거를 공유하되 독자를 위한 관점이 다름. 핵심 정의·조건·식은 각 문서에 필요한 만큼 반복해도 됨. 소유 문서로 옮겼다는 이유로 다른 문서의 이해에 필수인 전제를 링크 하나로 대체하지 않음.

**각 최신 문서는 단독으로 완결**

- 해당 PDF 또는 단일 HTML 하나로 목적·문제·모델·기호·단위·핵심 식·수치의 조건·결론·한계를 이해할 수 있어야 함.
- 이전 판, 개발 대화, Grand Challenge 연구 일지, 실행 코드가 필수 독서가 되면 안 됨. 이들 링크는 재현·세부 근거를 위한 선택 자료.
- 버전 번호는 판본 식별·이전 판 보존용. 본문을 변경점 요약이나 이전 판의 보충자료로 쓰지 않음.
- 앞부분에서 실험 측정값, 목표 자료로 적합한 결과, 독립 입력의 조건부 예측, 수치 fixture를 구별. 비교 표에도 동일한 구분 유지.
- 아직 알려지지 않은 것과 불가능한 주장의 조건을 최신 사실로 서술. “다음 버전에 구현” 같은 개발 계획으로 설명을 대신하지 않음.

**보존을 기본으로 한 개정**

1. 최신 과학 본문 전체와 관련 이전 판의 내용 목록을 먼저 확인. 정의·가정·식·증명·반례·그림·표·수치·참고문헌별 의미 단위를 식별.
2. 각 단위를 `유지 / 확장 / 다른 절로 통합 / 오류 정정 / 역할에 맞게 이동`으로 매핑. 위치와 이유를 Grand Challenge의 coverage 기록에 보관.
3. 이유 없는 누락 금지. 중복 통합은 필요한 조건과 반례까지 남겼을 때만 허용. 핵심 내용을 제거하고 “이전 버전 참조”로 대체하지 않음.
4. 잘못된 식이나 과도한 주장을 그대로 유지하는 것을 내용 보존으로 보지 않음. 올바른 정식화와 성립 조건으로 교정하고, 유의미한 실패 사례는 본문에 독립적인 반례로 남김. 변경 전후·교정 이력은 Grand Challenge에만 기록.
5. 모델 간 비교는 과학 내용이므로 유지. “vA보다 vB가 개선” 대신 각 모델의 가정·입력·정규화·정확도·적용 영역을 직접 정의해 비교.
6. 기존 판본과 그때의 원시 결과는 보존. 새 판에서 과거 수치를 사용하면 해당 계산의 모델·조건·출처를 명시. 원시 데이터의 파일명에 남은 버전 식별자는 provenance로 허용하되 독자에게 이전 본문을 요구하지 않음.

**개발 기록의 단일 위치**

새 개발 변경점, 커밋·작업 순서, 이전 판 대비 차이, 편집상의 삭제·이동 이유, 빌드/테스트 이력, 보존 점검표는 **`docs/grand_challenge/`에만 작성**. 세 과학 본문·그 부록·화면 footer에 개발 일지나 changelog를 넣지 않음.

이미 보존된 옛 판의 개발 기록은 역사 자료로 원형 유지. 현행 과학 문서의 본문이나 읽기 순서로 승격하지 않음. 최신 문서의 수치 출처·소프트웨어 방법·재현에 필요한 모델 식별은 과학적 provenance이며 개발 일지와 구분.

**Quotient의 수학적 계약**

- 노드·사상·관계의 의미와 화살표 방향을 먼저 정의. 계산의 데이터 의존성, 논리적 함의, 증거 관계, 비교 관계를 같은 화살표로 합치지 않음.
- 동치관계와 보존하는 관측량을 지정했을 때만 quotient라 부름. 가정을 더하는 것, 물리 효과를 버리는 것, 단위를 바꾸는 것은 자동으로 동일한 quotient가 아님.
- Preorder를 동치로 나눈 partial order, 물리 모델의 포함/정보 순서, 숫자 해상도의 refinement, 실험 검증 범위를 구별. 순서가 정의되지 않으면 비교 불가능함을 허용.
- Join/meet, 전체 lattice, N-free/series-parallel, commutative diagram 등은 필요한 조건을 증명한 범위에서만 사용. 보기 좋은 일렬 순서에 맞추려고 실제 분기·합류·비가환성을 지우지 않음.
- 대수 항등식·GKSL/CP·QRT 일치·수치 수렴·독립 입력·실험 holdout은 서로 다른 증거. 하나의 통과가 다른 주장으로 이어지는 허위 함의 금지.

**Grand Challenge 결과를 반영하는 기준**

- 연구 코드를 구현했다는 사실 자체는 과학 본문의 핵심 결과가 아님. 그 코드로 확인한 식·가정·반례·정량 결과와 한계를 적절한 문서에 반영.
- 내부 모델이 검증됐으면 analytic에 유도와 검증 범위, quotient에 해당 명제의 조건/근거를 반영. 실제 장치 검증이 없으면 squeezing report에 그 제한을 명시.
- 수치/실험 대조나 frontier가 갱신되면 squeezing report가 결과를 소유. analytic에는 필요한 이론적 원인·검증 예제, quotient에는 결론에 필요한 조건만 동기화.
- 과제 완료 후에도 fitting/independent input/holdout, numerical/physical error, source/detector noise와 적용 도메인의 구분 유지. 성공한 한 조건을 모든 조건으로 확대하지 않음.
